# CI/CD: how stacks are defined, wired and deployed

The pipeline (`.gitlab-ci.yml` or `.github/workflows/`) and the deploy tasks are generated by the
project type. Never edit generated files (projen overwrites them) or `projenrc/cre/` (installed from
the template; a change there goes to `cre-demo-template` via an MR).

## The CDK app is the definition

The pipeline is generated from the CDK app. Every top-level stack is a `CreStack` that says how it
is deployed, and every parameter the pipeline passes is a `CreCfnParameter` that says where its
value comes from. `npx projen` synthesizes the app (no bundling, no asset staging: seconds, not
minutes), reads what `CreApp` recorded, and writes the committed `cre-stacks.json` and one deploy
job per stack from it. Nothing is listed anywhere else.

**After adding, removing or rewiring a stack or a parameter, run `npx projen` and commit
`cre-stacks.json` with the generated CI.** CI never regenerates files: its build fails with "the CDK
app's stacks changed since cre-stacks.json and the pipeline were generated" until you do.

## Adding a top-level stack

```ts
import { Aws } from 'aws-cdk-lib';
import { CreApp, CreCfnParameter, CreStack, CreStackProps } from '@cre/constructs';

const app = new CreApp();

class StorageStack extends CreStack {
  public readonly bucket: s3.Bucket;
  constructor(scope: Construct, id: string, props: CreStackProps) {
    super(scope, id, props);
    this.bucket = new s3.Bucket(this, 'Data');
  }
}

interface ApiStackProps extends CreStackProps { readonly storage: StorageStack }
class ApiStack extends CreStack {
  constructor(scope: Construct, id: string, props: ApiStackProps) {
    super(scope, id, props);
    // Another stack's value: adds the output to StorageStack, this parameter here; the pipeline
    // passes one to the other and deploys ApiStack after StorageStack.
    const bucketName = new CreCfnParameter(this, 'BucketName', {
      from: { stack: props.storage, value: props.storage.bucket.bucketName },
    });
    // A deploy variable (GitLab CI/CD variable, GitHub secret, or local env).
    const domain = new CreCfnParameter(this, 'Domain', { fromVariable: 'DOMAIN' });
  }
}

const storage = new StorageStack(app, app.stackId('storage'), { region: 'us-east-1' });
new ApiStack(app, app.stackId('api-us-east-1'), { region: 'us-east-1', storage });
app.synth();
```

- **Name:** `app.stackId('<name>')` (`<project>-<name>`), or `app.stackId()` for the project name
  itself. The id is the deployed stack name and the CI job's name (`deploy:<project>-<name>`). Put
  the region in the name of a stack deployed to several regions (`api-us-east-1`). Never a role word:
  no "main", "primary", "secondary" or "home" stack or region; name stacks for what they hold.
- **`region` (required):** the literal region the pipeline deploys it to, in the project's
  `partition`. It is not the CDK `env`: the template stays region-agnostic (Rule 3).
- **`dependsOn` (optional):** stacks it deploys after without taking any of their values. A
  stack already deploys after every stack a `CreCfnParameter` takes a value from.
- **`assumeRole` / `executionRole` (optional):** the deploy variables holding the roles, `'$VAR'`
  (required) or `'$VAR?'` (may be empty). The deploy assumes `assumeRole` first (to reach another
  account; empty means the pipeline's own identity, `AWS_CREDS_TARGET_ROLE`) and hands CloudFormation
  `executionRole` (default `'$CFN_EXECUTION_ROLE_ARN'`; an empty optional one falls back to it).
  Never a role ARN or an account.

### Parameters

| Value comes from | Declare |
|---|---|
| another top-level stack | `new CreCfnParameter(this, 'X', { from: { stack, value } })`; `outputName` when the producer's output name differs from `'X'` |
| a deploy variable | `new CreCfnParameter(this, 'X', { fromVariable: 'VAR' })`; `optional: true` for one that may be empty |
| nothing: a fixed default | `new CfnParameter(this, 'X', { default: '...' })`; never passed |

- `type` defaults to `String`; give the CloudFormation type when it isn't (`AWS::EC2::VPC::Id`,
  `Number`, `CommaDelimitedList`).
- A parameter without a default that isn't a `CreCfnParameter` fails the synth, naming it.
- `from` reuses an output the producer already has under that name if the value is the same (e.g.
  a `CreEdgeOrigin`'s `Edge<Route>AlbArn`), and refuses a different value under that name.
- In a nested stack, a `CreCfnParameter` is declared on its top-level stack and CDK passes the value
  down; nothing else to do.
- The library's stacks already do this: `CreEdgeStack` takes each route's ALB from its
  `CreEdgeOrigin` and `BindleId` from `BINDLE_ID`; `CreDashboardStack` takes the edge's URLs when given
  `edge`; `CrePeeringStack` takes each `CreNetworkStack`'s VPC; `CreDnsStack` takes `DOMAIN` and
  `HOSTED_ZONE_ID`, and `addPrivateApi({ domains })` each region's endpoint.

### Placement the synth and `npx projen` enforce

| Stack | Region | Partition |
|---|---|---|
| `CreIamStack` (shared IAM) | its partition's IAM control-plane region | any |
| `CreDnsStack` (public records) | its partition's Route 53 control-plane region | any |
| `CreEdgeStack` (CloudFront + CloudFront Signer) | a CloudFront Signer region (us-east-1) | `aws` only |
| every other stack | any region in the project's `partition` | |

| partition | IAM control plane | Route 53 control plane |
|---|---|---|
| `aws` | us-east-1 | us-east-1 |
| `aws-us-gov` | us-gov-west-1 | us-gov-west-1 |
| `aws-cn` | cn-north-1 | cn-northwest-1 |
| `aws-eusc` | eusc-de-east-1 | eusc-de-east-1 |

`CreIamStack` and `CreDnsStack` also carry a CloudFormation Rule that refuses any other region at
deploy time. A CloudFront distribution can't use a VPC origin in another partition.

## Pipeline variables come from the stacks

Every variable the deploy reads is named by a stack (`fromVariable` parameters and roles, plus
`CFN_EXECUTION_ROLE_ARN` when a stack uses the default execution role). `cre-stacks.json` lists them
under `environment` (`required`, `optional`); the deploy also always needs `ASSETS_BUCKET_PREFIX`,
and fails fast on an empty required variable. `BINDLE_ID` has a default.

- **The same names on both providers.** The pipeline's own deploy role is `AWS_CREDS_TARGET_ROLE`
  everywhere (GitLab's credential vendor assumes it; on GitHub the OIDC credentials step does), and
  every other variable has the same name as a GitLab CI/CD variable or a GitHub secret.
- **GitLab:** project CI/CD variables reach every job; each stack job's `variables:` reference them
  by name. A default (`BINDLE_ID`) is a pipeline variable, which a project variable overrides.
- **Reserved names.** A project CI/CD variable outranks a GitLab job's own variables, so a variable
  named like one the deploy sets would silently replace it. `npx projen` refuses a `fromVariable`,
  `assumeRole` or `executionRole` with one of those names, and setup refuses to create one:
  every stack job variable (below), `ASSETS_PREFIX`, `PROJECT_NAME`, `CRE_ROLE_ASSUMED`, and any
  `STACK_*` (the names outputs travel under).
- **GitHub:** each stack job's `env` is generated with the variables that stack uses, each from the
  repository secret of the same name. Add the secret; don't edit the workflow.

## Rule 1: stacks talk through outputs and parameters, never exports

A value one stack needs from another goes through a `CreCfnParameter` with `from`: an output in the
producer, a parameter in the consumer, and the pipeline passes it. Nothing is matched by name, so
two stacks in different regions can both output `VpcId`.

- **Never `exportName` / `Fn.importValue`, and never use another stack's token directly** (CDK turns
  that into an export/import pair). Exports lock both stacks, can't cross regions or accounts, and
  make the deploy order CDK's. `check:stack-wiring` fails the build on any `Export`,
  `Fn::ImportValue` or `crossRegionReferences` resource.

## Rule 2: every top-level stack is a CreStack under a CreApp

- `CreApp` strips CDK metadata from every template, records the stacks for the pipeline, and fails
  the synth on a top-level stack that isn't a `CreStack`, a stack not named `<project>` or
  `<project>-<name>`, or a parameter without a default or a source.
- `CreStack` always uses the asset-bucket synthesizer (`${AssetsBucketName}` /
  `${AssetsBucketPrefix}`), declares those two parameters (the deploy passes them to every stack),
  is named by its id, and refuses `env`, `stackName` and `synthesizer`.
- `check:stack-plan` (right after synth) fails the build when the app differs from `cre-stacks.json`,
  a template lacks a parameter or output the plan names, or a generated job disagrees with the plan.

## Rule 3: no region, account or partition literals inside stacks

Every template is environment-agnostic; the `region` prop decides where it goes. Inside a stack,
refer to where it is deployed only through the pseudo parameters, always in this one form:

```ts
import { Aws } from 'aws-cdk-lib';
const arn = `arn:${Aws.PARTITION}:ssm:${Aws.REGION}:${Aws.ACCOUNT_ID}:parameter/${name}`;
const host = `ssm.${Aws.REGION}.${Aws.URL_SUFFIX}`;
```

- Use `Aws.REGION`, `Aws.ACCOUNT_ID`, `Aws.PARTITION`, `Aws.URL_SUFFIX`, `Aws.STACK_NAME` in
  template strings. Not `cdk.Aws.*`, `Fn.sub('${AWS::Region}')`, `Fn.ref('AWS::AccountId')` or
  `Stack.of(this).region` / `.account` / `.partition`: one spelling, so a review can grep for it.
- Never a region string, `arn:aws:` or an `amazonaws.com` endpoint: the same templates must deploy
  to any region and partition (commercial, GovCloud, China, EUSC). Service principals
  (`new iam.ServicePrincipal('ecs-tasks.amazonaws.com')`) are the exception: they are the same name
  in every partition.
- A stack that must be in one region asserts it at deploy time with a CloudFormation Rule on
  `AWS::Region` (`requireDeployRegion`, or `CreIamStack` / `CreDnsStack` for the control-plane
  regions).
- Region names as data (the regions a DNS record points into) come from other stacks' `region`
  props (`stack.deployRegion`).

## Rule 4: the pipeline only calls projen tasks

Every step that builds, tests, packages, publishes or deploys is a projen task: `npx projen build`
/ `ci:build:*` (the GitLab build jobs call these through their `yarn` aliases), and
`deploy:upload`, `deploy:stack` and `deploy:prune` in the deploy jobs. The only commands a job runs
directly are the ones specific to the CI system or the repo: checkout, toolchain and dependency
installs, caches and artifacts, credentials, and the provider's own gating.

One exception, forced by the runner image: GitLab's `build:docker` job runs
`sh projenrc/cre/scripts/build/build-docker.sh` (the script behind the `build:docker` task) because
the kaniko image has no node. Container images are otherwise projen tasks on both providers:
`build:container-plan` and `build:docker` in the build, `deploy:docker` (crane push, to the regions
of the stacks that use each image) inside `deploy:upload`. Don't add exceptions.

## How a change gets deployed

Nobody pushes to `main` (setup closes it after the first push): every change is an MR/PR from
`npx projen push`, and it deploys when it merges.

- **GitLab:** `main` is protected with push = No one. `npx projen push` opens the MR with
  auto-merge (squash); the MR pipeline builds and tests; GitLab merges when it passes; the `main`
  pipeline runs the deploy jobs.
- **GitHub:** `main` is protected (the `build` check and one approval). `npx projen push` opens
  the PR with the `auto-approve` and `auto-merge` labels. projen's workflows do the rest: `build`
  runs on the PR, `auto-approve` approves a trusted author's labelled PR, `auto-queue` enables
  auto-merge (squash), and GitHub merges once the build check passes. The merge is a push to
  `main`, which runs `deploy.yml`: it builds that commit and runs the deploy jobs. A PR never
  deploys, and the runner role trusts only `main`'s OIDC subject. projen's
  workflows push, open PRs and merge with the builder's GitHub App (`github.appSlug`; secrets
  `PROJEN_APP_ID`, `PROJEN_APP_PRIVATE_KEY`), the only credential they use: a merge
  made with the workflow's own token would not trigger `deploy.yml`. The weekly `upgrade-main` PR is
  opened by the App's bot, auto-approved and merged when its build passes, and deploys like any change.
- **Redeploy without a change:** GitLab, run a pipeline on `main`; GitHub, `gh workflow run deploy`.

## Rule 5: one deploy job per stack, all generated

| Job (GitLab / GitHub) | Runs | Needs |
|---|---|---|
| `deploy:upload` / `deploy-upload` | `npx projen deploy:upload`: every stack region's bucket is checked, then templates, assets and images are published | the build (GitHub: the deploy workflow's `build` job) |
| `deploy:<stack>` / `deploy-<stack>` | `npx projen deploy:stack` | `deploy:upload`, and the jobs of every stack it deploys after |
| `deploy:prune` / `deploy-prune` | `npx projen deploy:prune`: old asset prefixes removed (keeps current + 2) | every stack job |

- **Deploy order:** every stack after the stacks it depends on (`CreCfnParameter` sources and
  `dependsOn`), otherwise in the order the app creates them. Stacks that need nothing from each
  other deploy in parallel in CI. A cycle fails `npx projen`.
- **Every stack job has the same variables, built into the pipeline**, and `deploy:stack`
  resolves nothing: `STACK_NAME`, `TEMPLATE_NAME`, `AWS_REGION`, `AWS_DEFAULT_REGION`,
  `ASSETS_BUCKET`, `OUTPUTS_PREFIX`, `OUTPUTS`, `ROLE_ARN`, `ASSUME_ROLE`, `STACK_PARAMETERS`,
  `REQUIRED_VARS`, `REQUIRED_OUTPUTS`. `STACK_PARAMETERS` references the deploy variables and the
  earlier stacks' outputs directly. `cre-stacks.json` records every job's needs and variables.
- **Outputs travel as job data:** each stack job writes the outputs later stacks take to
  `dist/<stack>.env` (`<OUTPUTS_PREFIX>_<OUTPUT>`). GitLab passes it as a dotenv artifact to the jobs
  that need it; GitHub uploads it and the jobs that need it load it into their environment. At most
  20 per stack (the default dotenv limit of a self-managed GitLab).
- **Before deploying, a stack job checks its inputs:** an empty required variable or a missing output
  stops it, naming the variable, or the stack and output.
- **Roles:** every job runs as `AWS_CREDS_TARGET_ROLE`. A stack with an `assumeRole` assumes it
  from those credentials first (role chaining), so the other account's role trusts the runner role,
  which `setup:dns` sets up.
- **Serialised per job across runs** (GitLab `resource_group`, GitHub `concurrency`), and never
  cancelled mid-CloudFormation.

`npx projen deploy` runs the same jobs on your machine. It checks your credentials are for the
account in `cre-setup.json`, builds (`--no-build` skips), gets every variable the jobs need (your
environment, then `.cre/deploy.env`, which setup writes, then a prompt on a terminal), and runs
`deploy:upload`, `deploy:stack` once per stack in deploy order with exactly that job's variables,
then `deploy:prune`. `--stack <id>` deploys only that stack, reading the outputs it needs from the
deployed stacks. The identity differs from CI's (yours, not the runner role's): a stack whose
`assumeRole` trusts only the runner role (a cross-account `CreDnsStack`) is refused before anything
deploys; let CI deploy it.

A stack in a new region, or a new `fromVariable`, needs setup first (that region's bucket, that
CI/CD variable). The build's `check:deploy-prereqs` fails until it is done, naming the
`npx projen setup:aws` / `setup:repo prepare --var …` command. A `noEcho` parameter's variable must
be set with `:masked` (GitLab; GitHub secrets always are). A removed or renamed stack stays
deployed: `npx projen stacks` lists such orphans, and `npx projen teardown --orphans` deletes them
(it prints first; `--yes` deletes, once the user agrees).

## Before pushing

`npx projen build` regenerates the plan and CI, synthesizes every stack, runs `check:stack-wiring`,
`check:stack-plan` and `check:deploy-prereqs`, then the tests; it must pass, and `cre-stacks.json` and the CI files must be
committed with the code.
